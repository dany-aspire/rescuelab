# RL-005 Customer Ticket

## Title

All containers are healthy, but browser API requests fail in the production overlay

## Customer report

The production-style stack starts and Docker reports the database and API as healthy. The web page itself loads, but it shows a degraded service state and cannot load incident records. Requests through the web endpoint fail after deployment-specific API settings were reorganized.

The existing PostgreSQL volume and incident records must be preserved.

## Reproduction

1. Work from `incident/rl-005`.
2. If the worktree has no local `.env`, copy `.env.example` to the ignored local `.env`.
3. Reuse the existing Compose project and PostgreSQL volume.
4. Validate and start the combined configuration:
   `docker compose -p rescuelab -f compose.yaml -f compose.production.yaml ...`
5. Inspect service health, API startup logs, Nginx upstream errors, resolved non-secret port configuration, and safe in-network HTTP/TCP behaviour.
6. Compare direct API-container health with requests routed through Nginx.
7. Confirm that existing database records remain intact.

## Expected behaviour

- PostgreSQL and API become healthy.
- Nginx routes `/api/` requests to the API's actual listening port.
- <http://localhost:8080/api/health> returns HTTP 200 JSON.
- Existing incidents load.
- A new incident persists after browser refresh.

## Constraints

- Diagnose from current runtime evidence, resolved configuration, logs, proxy configuration, and safe network tests.
- Do not compare against `main` or inspect the scenario-creation diff.
- Do not delete or reset PostgreSQL data.
- Do not expose credential values.
- Do not change application or configuration files before repair approval.

## Acceptance criteria after approval

- The API listening port and Nginx upstream port agree through an explicit, documented configuration.
- API health and proxied health both return HTTP 200 JSON.
- Backend tests and frontend production build pass.
- Combined Compose validation passes.
- The complete stack starts without deleting the database volume.
- Existing incidents load.
- Browser incident creation and refresh persistence pass.
- Diagnosis and verification are documented in the required artifacts.
