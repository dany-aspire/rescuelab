# RL-008 Customer Ticket

## Title

API container is healthy, but the production gateway cannot reach it

## Customer report

The production-style stack starts and Docker reports both PostgreSQL and the API
as healthy. Nginx serves the web application on <http://localhost:8080>, but
proxied API requests return gateway errors. The UI reports a degraded service
and cannot load or create incidents.

The API's own in-container health check succeeds, yet requests made from the web
container to the API service fail. This appeared after the server startup
configuration was tightened for deployment. Existing PostgreSQL data must be
preserved.

## Reproduction

1. Work from `incident/rl-008`.
2. If the worktree has no local `.env`, copy `.env.example` to the ignored
   local `.env`.
3. Reuse the existing Compose project and PostgreSQL volume.
4. Build and recreate the production-style stack with `compose.yaml` and
   `compose.production.yaml`.
5. Confirm container health and reproduce the browser/gateway failure.
6. Compare API reachability from inside the API container with reachability from
   the web container over the Compose network.
7. Inspect the running process, listening sockets, service address resolution,
   ports, and gateway logs.
8. Confirm all existing database records remain intact.

## Expected behaviour

- PostgreSQL and API remain healthy.
- The API is reachable from other containers through the Compose service
  address and configured port.
- Proxied health and incident requests return HTTP 200 JSON.
- Existing incidents load.
- A browser-created incident persists after refresh.

## Constraints

- Diagnose from current container health, process/socket state, service-network
  reachability, logs, HTTP responses, and configuration.
- Do not compare against `main` or inspect the scenario-creation diff.
- Do not delete or reset PostgreSQL data.
- Do not change application or configuration files before repair approval.
- Do not bypass Nginx or expose an unnecessary host port as the final fix.

## Acceptance criteria after approval

- The API listens on the intended container interfaces and configured port.
- API-container health remains healthy.
- The web container can reach `api:3000/api/health`.
- Nginx-proxied health and incident listing return HTTP 200 JSON.
- Backend tests and frontend production build pass.
- Compose validation and image builds pass.
- The complete stack starts without deleting the database volume.
- Existing incidents remain present and a new browser-created incident persists
  after refresh.
- Diagnosis and verification are documented in the required artifacts.
