# RL-007 Customer Ticket

## Title

Split-origin deployment works by direct API request but fails in the browser

## Customer report

The production-style database, API, and web containers all start successfully.
The API health and incident endpoints return valid JSON when called directly on
<http://localhost:3000>. The web application loads on
<http://localhost:8080>, but the browser reports a degraded service, shows no
incidents, and cannot create a new incident.

This began after the frontend and API were deployed on separate origins. Existing
PostgreSQL data must be preserved.

## Reproduction

1. Work from `incident/rl-007`.
2. If the worktree has no local `.env`, copy `.env.example` to the ignored
   local `.env`.
3. Reuse the existing Compose project and PostgreSQL volume.
4. Build and recreate the stack with `compose.yaml`,
   `compose.production.yaml`, and `compose.split-origin.yaml`.
5. Confirm the frontend is served on port 8080 and the API directly on port 3000.
6. Compare direct HTTP results with browser console/network behaviour.
7. Inspect request and response headers for simple and preflighted cross-origin
   requests.
8. Confirm all existing database records remain intact.

## Expected behaviour

- PostgreSQL and API remain healthy.
- Direct API health returns HTTP 200 JSON.
- The browser loaded from port 8080 can read health and incidents from port 3000.
- Browser incident creation succeeds and persists after refresh.
- Cross-origin access is restricted to the intended frontend origin.

## Constraints

- Diagnose from current runtime behaviour, browser evidence, request/response
  headers, container configuration, and application configuration.
- Do not compare against `main` or inspect the scenario-creation diff.
- Do not delete or reset PostgreSQL data.
- Do not change application or configuration files before repair approval.
- Do not disable browser security or use a permissive wildcard as the final fix.

## Acceptance criteria after approval

- The intended frontend origin receives the correct CORS response headers.
- A disallowed origin does not receive CORS authorization.
- Browser GET requests for health and incidents succeed.
- Browser POST creation and its OPTIONS preflight succeed.
- Backend tests and frontend production build pass.
- Compose validation and image builds pass.
- Existing incidents remain present and a new browser-created incident persists
  after refresh.
- Diagnosis and verification are documented in the required artifacts.
